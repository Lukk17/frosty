# Platform notes

Facts about Plasma, KWin, Darkly and makepkg that Frosty depends on, each checked in the source named next to it. Versions checked: plasma-workspace v6.7.5, KWin v6.7.5, Darkly v0.5.41, Dolphin v26.08.3, KConfig 6.31, pacman 7.1.

---

### Global theme

1. Every global theme package falls back to `org.kde.breeze.desktop` for files it does not have (plasma-workspace [shell/packageplugins/lookandfeel/lookandfeel.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/packageplugins/lookandfeel/lookandfeel.cpp) lines 53 to 61, `setFallbackPackage`). Frosty ships its own `contents/layouts`, so only the splash screen comes from Breeze. Measured in the container: for a global theme without `layouts`, `filePath("layouts")` and `filePath("splashmainscript")` both return the Breeze files.
2. `KLookAndFeelManager::packageContents` sets the `DesktopLayout` flag from `pkg.filePath("layouts")` and the `SplashScreen` flag from `pkg.filePath("splashmainscript")` ([libklookandfeel/klookandfeelmanager.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/libklookandfeel/klookandfeelmanager.cpp) lines 90 and 92).
3. The layout is not applied by default. `plasma-apply-lookandfeel` adds the layout only with `--resetLayout` ([kcms/lookandfeel/tool/lnftool.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/kcms/lookandfeel/tool/lnftool.cpp) line 100), and the Global Theme page in System Settings clears the layout choices when a theme also has appearance settings (`resetSelectedContents`, [kcms/lookandfeel/kcm.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/kcms/lookandfeel/kcm.cpp) lines 533 to 541). The layout is applied only if you tick it on that page.
4. The splash screen is applied, because `SplashScreen` is part of the appearance settings. Lines 583 to 591 of `klookandfeelmanager.cpp` read `[ksplashrc][KSplash] Theme` from `contents/defaults` and, when it is empty, use the global theme id. Measured in the container: applying Frosty writes `Theme=com.github.lukk17.frosty` into `~/.config/kdedefaults/ksplashrc` and removes the user's own `Theme` line from `~/.config/ksplashrc`. ksplashqml loads the theme as a global theme package ([ksplash/ksplashqml/splashwindow.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/ksplash/ksplashqml/splashwindow.cpp) lines 108 to 117), so its `splashmainscript` is the Breeze file found through the same fallback. So applying Frosty switches the splash screen to the Breeze one. There is no value for `contents/defaults` that keeps whatever splash screen is set now. Naming one splash screen there, for example `Theme=com.github.vinceliuice.Layan`, keeps that one only.
5. A color scheme named in `contents/defaults` is found by `KLookAndFeelManager::colorSchemeFile` (same file, line 399). It removes characters that are not letters or digits, makes the next letter a capital, and looks for a file whose name ends in that text plus `.colors`, so `Layan-glass` becomes `LayanGlass`. A package that ships `contents/colors` uses that copy instead. Frosty ships `contents/colors`.
6. Applying a global theme writes its values into the files in `~/.config/kdedefaults/`, removes your own value of the same key from the file in `~/.config/`, and writes the theme id into `~/.config/kdedefaults/package`.
7. When colors are applied, the color scheme applier fills `[Colors:Header][Inactive]` from `[Colors:Window]` unless the accent colour tints the header (plasma-workspace [kcms/colors/colorsapplicator.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/kcms/colors/colorsapplicator.cpp) lines 249 to 269). The inactive title bar therefore gets the see-through window colour.

### Desktop layout

Checked in plasma-workspace v6.7.5, libplasma v6.7.5, kpackage v6.31.0 and the [Plasma scripting API](https://develop.kde.org/docs/plasma/scripting/api/).

1. Applying the layout replaces the whole desktop. `ShellCorona::loadLookAndFeelDefaultLayout` deletes every group of `plasma-org.kde.plasma.desktop-appletsrc` and loads again ([shell/shellcorona.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/shellcorona.cpp) lines 689 to 714). Panels, desktop widgets and the wallpaper settings are gone afterwards, and the desktop gets the default wallpaper.
2. Adding a widget whose plugin is not installed does not fail. `PluginLoader::loadApplet` returns a placeholder that shows "Could not find requested component" (libplasma [src/plasma/pluginloader.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.7.5/src/plasma/pluginloader.cpp) line 145), and `Containment::addWidget` hands it back to the script (plasma-workspace [shell/scripting/containment.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/scripting/containment.cpp) lines 203 to 209). The Frosty layout therefore checks `knownWidgetTypes` first, which the API page describes as "this lists all plasmoid types", and skips a widget that is not installed. Measured: without the third-party widgets the panels hold only the installed widgets and plasmashell logs no "Could not find" line.
3. The system tray removes items from `extraItems` and `knownItems` whose plugin is not installed when it starts (`PlasmoidRegistry::sanitizeSettings`, [applets/systemtray/plasmoidregistry.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/applets/systemtray/plasmoidregistry.cpp) line 151), so the layout writes the full tray lists in both cases. A tray widget with `X-Plasma-DBusActivationService` (battery, brightness, Bluetooth, media player) appears only while its D-Bus service runs ([applets/systemtray/dbusserviceobserver.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/applets/systemtray/dbusserviceobserver.cpp) line 59).
4. The scripting API has no handle for the widgets inside the system tray. Writing their config groups directly is undone by the running widget: `KConfigSkeleton` removes a key whose value equals the default when it saves (kconfig [src/core/kcoreconfigskeleton.cpp](https://invent.kde.org/frameworks/kconfig/-/blob/v6.31.0/src/core/kcoreconfigskeleton.cpp) line 297), and `Applet::configChanged` reloads only the widget itself (libplasma [src/plasma/applet.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.7.5/src/plasma/applet.cpp) line 844). Measured: the volume setting `showVirtualDevices` survived one container run and was lost in the next.
5. `writeConfig` writes under the widget's `Configuration` group, because `Applet::config()` returns it ([src/plasma/applet.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.7.5/src/plasma/applet.cpp) line 205). The `globalShortcut` property writes `[Shortcuts] global` next to `Configuration`, which is where `Applet::restore` reads it at start (same file line 144, called from `src/plasma/containment.cpp` line 438).
6. The script engine puts every new panel on screen 0 (`cg.writeEntry("lastScreen", 0)`, [shell/scripting/scriptengine.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/scripting/scriptengine.cpp) line 380).
7. A task manager launcher `preferred://browser` or `preferred://filemanager` is dropped when no default application of that kind exists ([libtaskmanager/launchertasksmodel_p.h](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/libtaskmanager/launchertasksmodel_p.h) lines 25 and 26). Launchers for `applications:` entries are kept even when the application is missing.
8. KPackage caches the list of installed widgets only for the first 20 seconds after a program starts (`maxCacheAge = 20`, kpackage [src/kpackage/private/packageloader_p.h](https://invent.kde.org/frameworks/kpackage/-/blob/v6.31.0/src/kpackage/private/packageloader_p.h) line 27). Widgets that `frosty-setup` installs while Plasma runs are therefore seen by a layout applied afterwards, without a restart. Measured in the container.

9. `screenCount` is the number of screens Plasma knows (`AppInterface::screenCount` returns `numScreens()`, [shell/scripting/appinterface.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/scripting/appinterface.cpp) line 44). A layout runs after Plasma has made a desktop for every screen (`loadDefaultLayout` calls `addOutput` for each screen first, [shell/shellcorona.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/shellcorona.cpp) lines 1118 to 1121).
10. Setting `panel.screen` calls `ShellCorona::setScreenForContainment`, which moves the panel view to that screen (`shell/scripting/containment.cpp` line 80, `shell/shellcorona.cpp` lines 2644 to 2689). `desktopForScreen(n)` returns the desktop of screen n (`shell/scripting/scriptengine_v1.cpp` line 186). Measured with one and with two KWin virtual outputs in the container.
11. `addWidget(name, x, y, width, height)` passes the position to the desktop's `createApplet` when x and y are 0 or more (`shell/scripting/containment.cpp` lines 182 to 197). The `geometry` property of a widget does nothing, its setter is commented out (`shell/scripting/widget.cpp` lines 170 to 180). The desktop stores positions per screen size in `ItemGeometries-<width>x<height>` (plasma-desktop [containments/desktop/package/contents/ui/main.qml](https://invent.kde.org/plasma/plasma-desktop/-/blob/v6.7.5/containments/desktop/package/contents/ui/main.qml) line 293).
12. A global shortcut belongs to one action, so only the dock on screen 0 gets Alt+F1 for AppGrid.

### Backup and restore in frosty-setup

Checked in konsave v2.3.0 (commit `765490b45065f0524994d2865722c99502f891c2`) and plasma-workspace v6.7.5.

1. `konsave -s <name>` copies the files listed in `~/.config/konsave/conf.yaml` into `~/.config/konsave/profiles/<name>` ([konsave/consts.py](https://github.com/Prayag2/konsave/blob/v2.3.0/konsave/consts.py) line 13, [konsave/funcs.py](https://github.com/Prayag2/konsave/blob/v2.3.0/konsave/funcs.py) lines 167 to 201). The KDE list includes `plasma-org.kde.plasma.desktop-appletsrc` ([konsave/conf_kde.yaml](https://github.com/Prayag2/konsave/blob/v2.3.0/konsave/conf_kde.yaml) line 57). konsave writes the KDE list on its first run only when `XDG_CURRENT_DESKTOP` is `KDE`, and a generic list otherwise ([konsave/__main__.py](https://github.com/Prayag2/konsave/blob/v2.3.0/konsave/__main__.py) line 117).
2. `konsave -e <name> -d <folder>` writes `<folder>/<name>.knsv`, a zip file, and adds the date and time to the name when that file exists (`funcs.py` lines 279 to 329, `consts.py` line 16).
3. Every konsave command catches its own errors, prints them and writes them to `~/.cache/konsave_log.txt` (`exception_handler`, `funcs.py` lines 27 to 56). Measured in the container: a failed `konsave -s` or `konsave -a` ends with exit status 0 when `~/.cache` exists, and with 1 only when the log cannot be written. A first run outside a KDE session printed "Profile saved successfully!" without saving `plasma-org.kde.plasma.desktop-appletsrc`. frosty-setup therefore checks the saved `appletsrc` and the `PK` start of the exported file instead of the exit status, and picks a backup name that does not exist yet.
4. `konsave -a <name>` copies the saved files back over the ones in `~/.config` (`funcs.py` lines 205 to 231). It does not save or restore `~/.config/kdedefaults`, where a global theme writes its values (Global theme point 6). So after `konsave -a`, the colors, icons and style of the Frosty global theme stay. Applying the previous global theme first and then `konsave -a` brings the old look back. Measured in the container: with Breeze Dark as the old look, all seven checked values (color scheme, widget style, icons, global theme, Plasma Style, cursors, window decoration) were the same as before.
5. Measured in the container: after the three go-back commands, the panels, the widgets and their settings were the same as before, except two things that a plain restart of plasmashell also does without Frosty: Plasma rounds a desktop widget position to its grid (99.1288 became 96), and the system tray adds a newly installed tray widget by itself (Dockio, enabled by default and not in `knownItems`, Desktop layout point 3).
6. frosty-setup reads the old widget settings from the backup copy of `plasma-org.kde.plasma.desktop-appletsrc` with the scripting `ConfigFile(file, group)` object, which reads any KConfig file ([shell/scripting/scriptengine.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.7.5/shell/scripting/scriptengine.cpp) line 173, `shell/scripting/configgroup.cpp` lines 140 to 172). The API page documents it as "ConfigFile(string file[, string group])". The lower case `configFile` is not defined in a script.
7. It writes the settings with `currentConfigGroup` and `writeConfig`, through `org.kde.PlasmaShell.evaluateScript` on D-Bus, which returns what the script prints (`shell/shellcorona.cpp` lines 2016 to 2046). `writeConfig` also updates the widget's loaded settings when the key is in its settings file (`shell/scripting/applet.cpp` line 103), and the script engine reloads the widget when it is done (`shell/scripting/widget.cpp` line 40). Measured: the AI usage widget showed its 10 old accounts right after the restore, without a restart.
8. Plasma writes changed widget settings to disk at most 10 seconds after the change (`CONFIG_SYNC_TIMEOUT = 10000`, libplasma [src/plasma/corona.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.7.5/src/plasma/corona.cpp) line 113).
9. Old and new widgets are paired by plugin id. When several have the same plugin, both lists are sorted by place (top panel, bottom panel, left, right, desktop), then screen, then the position in the panel (`Widget.index`) or on the desktop (widget id), and paired in that order. For a normal widget the `[Configuration]` group and its sub groups are copied. For the system tray, which is a containment, only its `[General]` group is copied. Keys that the old widget did not have keep the Frosty value.

### System Monitor sensors

Checked in ksystemstats v6.7.5.

1. `cpu/all/usage` and `cpu/all/averageTemperature` exist on every computer ([plugins/cpu/cpu.cpp](https://invent.kde.org/plasma/ksystemstats/-/blob/v6.7.5/plugins/cpu/cpu.cpp) lines 24, 100 and 154). The average temperature has a value only when the computer reports CPU temperatures.
2. `memory/physical/used`, `memory/physical/total`, `memory/swap/used` and `memory/swap/total` exist on every computer ([plugins/memory/backend.cpp](https://invent.kde.org/plasma/ksystemstats/-/blob/v6.7.5/plugins/memory/backend.cpp) lines 17 to 31).
3. `gpu/all` has only `usage`, `totalVram` and `usedVram`, summed or averaged over all GPUs ([plugins/gpu/AllGpus.cpp](https://invent.kde.org/plasma/ksystemstats/-/blob/v6.7.5/plugins/gpu/AllGpus.cpp) lines 16, 26 and 31). With two GPUs, `gpu/all/usage` is the average of both.
4. Each GPU is `gpu0`, `gpu1` and so on, numbered in the order udev lists the supported AMD, NVIDIA and Intel PCI devices ([plugins/gpu/LinuxBackend.cpp](https://invent.kde.org/plasma/ksystemstats/-/blob/v6.7.5/plugins/gpu/LinuxBackend.cpp) lines 49 to 74). Temperature and power exist only per GPU ([plugins/gpu/GpuDevice.cpp](https://invent.kde.org/plasma/ksystemstats/-/blob/v6.7.5/plugins/gpu/GpuDevice.cpp) lines 70 and 71), so `gpu/gpu0/temperature` and `gpu/gpu0/power` stay. On a computer with an integrated and a separate GPU, `gpu0` may be the integrated one, and the user picks the right sensor in the widget settings.

### Install message

1. The PKGBUILD manual: "To use this feature, create a file such as pkgname.install and put it in the same directory as the PKGBUILD script", with `post_install` getting the new version and `post_upgrade` the new and the old version (`man 5 PKGBUILD`, pacman 7.1).
2. The Arch package guidelines say "All important messages should be echoed during install using an .install file" and "To print data, use printf or echo", and that optional dependencies are printed by pacman and do not belong in the file ([Arch package guidelines](https://wiki.archlinux.org/title/Arch_package_guidelines)). The PKGBUILD wiki page adds "Do not end the script with exit" ([PKGBUILD](https://wiki.archlinux.org/title/PKGBUILD)). [packaging/aur/frosty.install](../packaging/aur/frosty.install) only prints text with `printf`.
3. pacman 7.1 refuses to run the functions when it cannot isolate the network, with the message `refusing to run "/usr/bin/bash" with network access; set DisableSandboxNetwork in pacman.conf to override`. Measured in a container started with `--cap-drop ALL`: with the normal settings the message is not printed, and on a reinstall with `DisableSandboxNetwork` in a copy of `pacman.conf` pacman prints it. A normal install on a real system was not tested.

### Defaults in /etc/xdg

Checked in kconfig v6.31.0, Konsole v26.08.2 and Dolphin v26.08.2.

1. Qt lists `"~/.config", "/etc/xdg"` as the Linux `GenericConfigLocation` ([QStandardPaths](https://doc.qt.io/qt-6/qstandardpaths.html)). KConfig reads every copy of a file in those folders when the `CascadeConfig` flag is set (`parseSystemConfigFiles`, kconfig [src/core/kconfig.cpp](https://invent.kde.org/frameworks/kconfig/-/blob/v6.31.0/src/core/kconfig.cpp) lines 717 and 867), and the file in `~/.config` is read last, so the user's own value wins.
2. `KSharedConfig::openConfig` uses `FullConfig`, which includes `CascadeConfig`, by default ([src/core/ksharedconfig.h](https://invent.kde.org/frameworks/kconfig/-/blob/v6.31.0/src/core/ksharedconfig.h) line 84), and so does `KCoreConfigSkeleton` ([src/core/kcoreconfigskeleton.cpp](https://invent.kde.org/frameworks/kconfig/-/blob/v6.31.0/src/core/kcoreconfigskeleton.cpp) line 1249). A settings class made by `kconfig_compiler` from a `kcfg` file passes the file name to that constructor ([src/kconfig_compiler/KConfigSourceGenerator.cpp](https://invent.kde.org/frameworks/kconfig/-/blob/v6.31.0/src/kconfig_compiler/KConfigSourceGenerator.cpp) line 269).
3. When a user changes such a setting back to the built-in default, KConfig still writes it, because the `/etc/xdg` value counts as a default (`cg.hasDefault(mKey)`, `src/core/kcoreconfigskeleton.cpp` line 297). The user's choice is kept.
4. Konsole reads `[Desktop Entry] DefaultProfile` with `KSharedConfig::openConfig()` ([src/profile/ProfileManager.cpp](https://invent.kde.org/utilities/konsole/-/blob/v26.08.2/src/profile/ProfileManager.cpp) lines 56 and 66) and picks the profile whose path ends in that file name (same file line 242). It finds profiles and color schemes in every `konsole` folder of the data folders, including `/usr/share/konsole` ([src/profile/ProfileReader.cpp](https://invent.kde.org/utilities/konsole/-/blob/v26.08.2/src/profile/ProfileReader.cpp) line 37, [src/colorscheme/ColorSchemeManager.cpp](https://invent.kde.org/utilities/konsole/-/blob/v26.08.2/src/colorscheme/ColorSchemeManager.cpp) line 107).
5. `ForceNewTabs` (group `KonsoleWindow`), `CloseTabOnMiddleMouseButton` and `ExpandTabWidth` (group `TabBar`) are entries of Konsole's settings class for `konsolerc` ([src/settings/konsole.kcfg](https://invent.kde.org/utilities/konsole/-/blob/v26.08.2/src/settings/konsole.kcfg) lines 6, 36, 170 and 203).
6. `OpenExternallyCalledFolderInNewTab`, `BrowseThroughArchives`, `ShowFullPath` and `TabStyle` are entries of Dolphin's settings class for `dolphinrc`, group `General` ([src/settings/dolphin_generalsettings.kcfg](https://invent.kde.org/system/dolphin/-/blob/v26.08.2/src/settings/dolphin_generalsettings.kcfg) lines 10, 17, 33, 41, 55 and 94). The settings page labels `TabStyle=FullWidth` "Tabs span the available width" ([src/settings/interface/folderstabssettingspage.cpp](https://invent.kde.org/system/dolphin/-/blob/v26.08.2/src/settings/interface/folderstabssettingspage.cpp) line 131).
7. Measured with `kreadconfig6` in a new user account in the container: every key reads the `/etc/xdg` value, and a value in `~/.config` wins.

### Window decoration

1. The decoration settings page lists a plugin without themes under its plugin id, with the theme name equal to the plugin's `Name` (KWin [src/kcms/decoration/decorationmodel.cpp](https://invent.kde.org/plasma/kwin/-/blob/v6.7.5/src/kcms/decoration/decorationmodel.cpp), `data.setThemeName(data.visibleName())`). For Frosty that gives `library=com.github.lukk17.frosty` and `theme=Frosty`.
2. The same page loads every decoration plugin into one process to list them (`KPluginFactory::instantiatePlugin` for each plugin, same file). The application style settings page does the same with styles. This is why the Frosty copy of Darkly has its own C++ namespace and not only its own file names.
3. The plugin id is the plugin file name without `.so`, because the plugin metadata has no `Id`. Darkly's id is `org.kde.darkly`, Frosty's is `com.github.lukk17.frosty`.

### Darkly translucency and package listing

1. Darkly makes whole windows translucent and blurred when the Window colour of the color scheme has an alpha below 255 (Darkly `kstyle/darklyhelper.cpp` lines 1883 to 1890, `kstyle/darklystyle.cpp` lines 433 to 506, `kstyle/darklyblurhelper.cpp` lines 162 to 171).
2. With `BlurTransparentTitleBar` set, the decoration takes the title bar colour from `[Colors:Header]` and its alpha from `ToolBarOpacity` in the `[Style]` group of the config file (Darkly `kdecoration/darklydecoration.cpp` lines 172 to 198 and 290 to 324).
3. Darkly's decoration reads `ToolBarOpacity` with a fallback of 100 written in the code, `readEntry("ToolBarOpacity", 100)` (Darkly `kdecoration/darklydecoration.cpp` line 193), not with the kcfg default. Frosty changed this fallback to 80 ([vendor/style/kdecoration/frostydecoration.cpp](../vendor/style/kdecoration/frostydecoration.cpp) line 193), so the title bar matches the tool bars without a `~/.config/frostyrc`.
4. The style moves the old `TransparentDolphinView` setting to `DolphinViewOpacity` only while `DolphinViewOpacity` is at its default. Darkly compares with 100 ([vendor/style/kstyle/frostystyle.cpp](../vendor/style/kstyle/frostystyle.cpp) line 2456 and [vendor/style/kstyle/config/frostystyleconfig.cpp](../vendor/style/kstyle/config/frostystyleconfig.cpp) line 381). Frosty compares with its own default of 80. KConfig does not write a value equal to the default into the file (`KConfigSkeletonGenericItem::writeConfig` in `kcoreconfigskeleton.h` calls `revertToDefault`), so a user who had an older Frosty default has no `DolphinViewOpacity` line and gets the new default.
5. Darkly's unit tests check the defaults. In Frosty they expect 80 and pass with `BUILD_TESTING=ON`. The package still builds with `BUILD_TESTING=OFF`, as the Darkly AUR package does.
6. KPackage lists a package only when its `metadata.json` names its structure in `KPackageStructure` (KPackage 6.31 `src/kpackage/packageloader.cpp` line 211). Layan and Breeze's own Plasma Styles do not, so `kpackagetool6` does not list them. Frosty's Plasma Style names `Plasma/Theme`.
7. Dolphin draws its full width status bar with `QStyle::PE_PanelStatusBar` (Dolphin [src/statusbar/dolphinstatusbar.cpp](https://invent.kde.org/system/dolphin/-/blob/v26.08.3/src/statusbar/dolphinstatusbar.cpp) line 473). Darkly draws nothing for this element, so the status bar shows the window background under it. Frosty draws it like a tool bar instead (`Style::drawPanelStatusBarPrimitive`). The bars and the Dolphin view erase the window background first and then draw their own colour.
8. A plain window area, with no bar or view on top, shows the Window colour exactly once, alpha 204, 80 percent cover. Qt fills it with `CompositionMode_Source` when `WA_NoSystemBackground` is off (Qt `QWidgetPrivate::paintBackground`), and the style clears that attribute for translucent windows ([vendor/style/kstyle/frostystyle.cpp](../vendor/style/kstyle/frostystyle.cpp) line 516). `Style::eventFilter` then fills it again with `CompositionMode_Source` (line 1759), which replaces Qt's fill instead of adding to it. Darkly filled with `CompositionMode_SourceOver`, and its `Style::eventFilter` ran twice for each event of a polished widget, because `Style` was both the filter of the widget and the filter of the application object. The Qt documentation of `QCoreApplication::notify` says a filter on the application object "is able to process all events for all widgets". Three layers of the earlier alpha 166 covered 96 percent. Frosty gives the application object its own filter, `ApplicationEventFilter` (line 177), so `Style::eventFilter` runs once.

### Blur behind Qt Quick windows

Checked in Qt 6.12.0, KWindowSystem 6.31.0, filelight 26.08.3, kcmutils 6.31.0 and plasma-workspace 6.8.2, measured in a container under Xvfb with X11 clients.

1. Darkly asks for blur only for widgets, through `BlurHelper::registerWidget` in `Style::polish(QWidget *)` ([vendor/style/kstyle/frostystyle.cpp](../vendor/style/kstyle/frostystyle.cpp) line 506). A Qt Quick window is a `QQuickWindow`, not a widget. Measured before the change: the filelight window has a 32 bit visual, so the Frosty Window colour makes it see-through, and it has no `_KDE_NET_WM_BLUR_BEHIND_REGION` property.
2. The style installs `ApplicationEventFilter` as the event filter of the application object (frostystyle.cpp line 234). The Qt documentation of `QCoreApplication::notify` says such a filter "is able to process all events for all widgets". Measured: it also gets the `Show` and `Resize` events of every `QQuickWindow`, and `Style::applicationEventFilter` passes them to `BlurHelper::updateQuickWindow` (frostystyle.cpp line 1829).
3. `KWindowEffects::enableBlurBehind` takes any `QWindow` (`KF6/KWindowSystem/kwindoweffects.h` line 78). On X11 it writes `_KDE_NET_WM_BLUR_BEHIND_REGION` also when no compositor runs. Measured after the change: the filelight window and a normal see-through QML `Window` got the property with round corners. A frameless, a `Qt.Popup` and an opaque QML `Window` did not, and filelight did not when `OpaqueApps=filelight` was set in `frostyrc`.
4. `QQuickRenderControl::renderWindowFor` returns what the render control's `renderWindow` reports, and the default `renderWindow` returns nullptr (`QtQuick/qquickrendercontrol.h` lines 45 and 46). The style skips a window for which it returns a window, and a hidden one. Measured: `kcmshell6 kcm_colors`, which shows its page in a `QQuickWidget`, had the same X windows and the same blur property before and after the change, so the off-screen window of the `QQuickWidget` got nothing.
5. Plasma panels, popups, on-screen messages and the desktop are frameless windows. `PanelView` sets `Qt::FramelessWindowHint | Qt::WindowDoesNotAcceptFocus` (plasma-workspace [shell/panelview.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.8.2/shell/panelview.cpp) line 75), `DesktopView` sets `Qt::Window | Qt::FramelessWindowHint` ([shell/desktopview.cpp](https://invent.kde.org/plasma/plasma-workspace/-/blob/v6.8.2/shell/desktopview.cpp) line 44), `PlasmaQuick::Dialog` sets `Qt::FramelessWindowHint` and keeps it for on-screen messages (libplasma [src/plasmaquick/dialog.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.8.2/src/plasmaquick/dialog.cpp) lines 738, 852 and 1183), and `PlasmaWindow`, the base of the newer popups, sets `Qt::FramelessWindowHint | Qt::WindowStaysOnTopHint` ([src/plasmaquick/plasmawindow.cpp](https://invent.kde.org/plasma/libplasma/-/blob/v6.8.2/src/plasmaquick/plasmawindow.cpp) line 45). The style skips frameless windows, and it does nothing at all in the application `plasmashell`. Applications whose name starts with `plasma-` are not skipped, although Darkly's `_isPlasma` test matches them (frostystyle.cpp line 244).
6. A real Plasma panel could not be checked. plasmashell 6.8.2 crashed in the container in its layout script (`KConfigGroup::writeEntry`, seen with gdb), also with the Fusion style, so the crash is not caused by Frosty. In `kwin_wayland --virtual` without `/dev/dri`, KWin said "Compositing is not active" and did not offer `org_kde_kwin_blur_manager`, so no blur request can be seen on Wayland there.
7. A colour change while the window stays the same size, for example a new color scheme, is not picked up until the next `Show`, `Resize` or `WindowStateChange` of that window.

### Colors of the Plasma Style

Checked in libplasma 6.8.2, KSvg 6.31.0 and Kirigami 6.31.0, measured in a container under Xvfb with picom.

1. KSvg colours the SVG frames of panels, popups and widget backgrounds through the style sheet of each SVG, and writes each colour with `QColor::name()`, which is `#rrggbb` without alpha (KSvg [src/ksvg/private/imageset_p.cpp](https://invent.kde.org/frameworks/ksvg/-/blob/master/src/ksvg/private/imageset_p.cpp), `svgStyleSheet`). It builds its `KColorScheme` objects with `QPalette::Active` only. Measured: the frames `widgets/background`, `dialogs/background`, `widgets/panel-background`, `widgets/tooltip` and `widgets/plasmoidheading` drew the same pixels with the solid and with the see-through `colors` file.
2. The Kirigami platform of libplasma (`KirigamiPlasmaStyle.so`) reads the Plasma Style `colors` file through `KColorScheme`, which keeps the alpha of a `r,g,b,a` entry. Measured with the earlier alpha 166: `Kirigami.Theme.backgroundColor` of the `Window` color set was `16,16,20,166`, for the active and the inactive color group. The file now has alpha 204, so it is `16,16,20,204`. The `Header` color set gave `68,69,75,255`, so `[Colors:Header][Inactive]` is not read there.
3. So a widget that fills its own shapes with `Kirigami.Theme.backgroundColor`, such as the cards of KDE Control Station (`contents/ui/lib/Card.qml` line 105), gets 80 percent glass. When the widget's own transparency option is on, it uses only the red, green and blue of that colour with its own level, so the alpha of the file does not matter there.

### Packaging

1. makepkg accepts only files as local sources, not folders (`get_filepath` in `/usr/share/makepkg/util/source.sh` checks `-f`). The AUR recipe [packaging/aur/PKGBUILD](../packaging/aur/PKGBUILD) therefore takes the release archive of the tag as its source, and reads the project from `$srcdir/frosty-<version>`, the top folder of a GitHub tag archive. The [PKGBUILD](../PKGBUILD) at the top sources that recipe, empties `source` and `sha256sums`, and makes `_frosty_root` return `$startdir`, which the PKGBUILD manual calls deprecated, so a local build reads this folder with the same steps.
2. makepkg uses `src/` and `pkg/` next to the PKGBUILD as its work folders, so this project keeps its sources in `vendor/` and never in `src/`.
3. KDE's `kde_configure_git_pre_commit_hook` acts only when `${CMAKE_SOURCE_DIR}/.git` exists (`/usr/share/ECM/kde-modules/KDEGitCommitHooks.cmake` line 63). The style is built from `vendor/style`, which has no `.git`, so a build never writes git hooks.
4. makepkg sources the PKGBUILD by its full path (`BUILDFILE` is made absolute in `/usr/bin/makepkg`), so `${BASH_SOURCE[0]}` inside [PKGBUILD](../PKGBUILD) finds [packaging/aur/PKGBUILD](../packaging/aur/PKGBUILD) from any folder. It copies the install file from `$startdir/$install` (`/usr/bin/makepkg`, the loop over `install/.INSTALL`), so `install=packaging/aur/frosty.install` works in the top PKGBUILD, and the AUR recipe keeps `install=frosty.install` next to itself.
5. The AUR action KSXGitHub/github-actions-deploy-aur v4.2.0 with `asset_dir` mirrors that folder into the AUR repository, deletes tracked files that the folder does not have, runs `updpkgsums` there when `updpkgsums` is true, and writes `.SRCINFO` with `makepkg --printsrcinfo` ([build.sh](https://github.com/KSXGitHub/github-actions-deploy-aur/blob/084b0d9b15415bf9cdb65d44dad1efe37a354050/build.sh)). So [packaging/aur](../packaging/aur) is the whole AUR repository, and the zeros in its `sha256sums` are replaced by the checksum of the real tag archive before the push.
6. ECM's `KDEClangFormat` copies its own `clang-format.cmake` to `.clang-format` in the source folder of a build when `clang-format` is installed and the file is missing (extra-cmake-modules 6.31 `kde-modules/KDEClangFormat.cmake` lines 57 to 69). Its documentation says the file "should not be added to version control", so [.gitignore](../.gitignore) lists `vendor/style/.clang-format`.
7. The style calls `include(CTest)` in `vendor/style/kstyle/CMakeLists.txt` and not at the top of `vendor/style`, so the build folder lists no tests at its top and `ctest` there says "No tests were found" and exits 0. Measured in the Arch container. [packaging/ci.sh](../packaging/ci.sh) therefore runs `ctest` in the `kstyle6` folder of the build, where the Qt 6 build of `kstyle` goes (`add_subdirectory(kstyle kstyle6)` in `vendor/style/CMakeLists.txt` line 153), with `--no-tests=error` so a run without tests fails.
8. GitHub runs a container job as root on a workspace owned by the runner user, so the user `builder` that runs makepkg cannot write in the project folder. makepkg then refuses even `--printsrcinfo` ("You do not have write permission for the directory $BUILDDIR"), measured in the container with the copy owned by another user. [packaging/ci.sh](../packaging/ci.sh) gives makepkg its own `BUILDDIR`, `SRCDEST` and `PKGDEST` in a folder owned by `builder`.
9. namcap 3.6.0 reads a PKGBUILD in a restricted bash without `dirname` and without `.` on a path with a slash, so it cannot read the [PKGBUILD](../PKGBUILD) at the top ("PKGBUILD is not a valid PKGBUILD") and still exits 0. Measured in the Arch container. [packaging/ci.sh](../packaging/ci.sh) runs namcap on [packaging/aur/PKGBUILD](../packaging/aur/PKGBUILD), which holds all the metadata, and fails on an `Error:` line as well as on an ` E: ` line.
10. The default `makepkg.conf` of Arch Linux has `debug` in `OPTIONS`, so a build also makes `frosty-debug`. namcap reports every `.build-id` link of that package as pointing to a missing file, because the target is in the main package. [packaging/ci.sh](../packaging/ci.sh) keeps only the main package for namcap and for the release.

### KDE Store archives

Checked in KNewStuff 6.31.0 and KPackage 6.31.0, with the knsrc files in `/usr/share/knsrcfiles`.

1. Plasma Styles (`plasma-themes.knsrc`) and Global Themes (`lookandfeel.knsrc`) use `Uncompress=kpackage`. KPackage takes the only folder of an archive as the package when the archive has exactly one entry at the top (kpackage [src/kpackage/private/packagejobthread.cpp](https://invent.kde.org/frameworks/kpackage/-/blob/v6.31.0/src/kpackage/private/packagejobthread.cpp) lines 221 to 232). The Frosty archives therefore hold one folder, `frosty` or `com.github.lukk17.frosty`, with `LICENSE` and `CREDITS.md` inside it.
2. Icons (`icons.knsrc`) use `Uncompress=true` with `TargetDir=icons`, and the color schemes (`colorschemes.knsrc`) use `Uncompress=archive` with `TargetDir=color-schemes`. Both copy the top of the archive straight into the target folder (knewstuff [src/core/installation.cpp](https://invent.kde.org/frameworks/knewstuff/-/blob/v6.31.0/src/core/installation.cpp) lines 405 to 416). The icon archive holds the one folder `frosty`. Color schemes are found as files directly in `color-schemes`, so that archive holds `Frosty.colors`, `Frosty.LICENSE` and `Frosty.CREDITS.md` at the top.
3. Cursors (`xcursor.knsrc`) use `Uncompress=subdir-archive` with `InstallPath=.icons`. An archive with more than one entry at the top is put into a new folder named after the archive file, one with a single entry is copied as it is (same file, lines 409 to 414). The cursor archive holds the one folder `Sweet-cursors`, so it lands in `~/.icons/Sweet-cursors`.
4. Store categories, from `https://api.kde-look.org/ocs/v1/content/categories`: Plasma Themes 104, Plasma Color Schemes 112, Full Icon Themes 132, Cursors 107, Global Themes (Plasma 6) 722.
